ATTEMPT 2 — correct (PASSED validation, byte-identical to the fixture):
    property and loan keys simply absent from the tool input
  -> "matches replay exactly: True". This is the behaviour the prompt asks for.

ATTEMPT 3 — all-null object (REJECTED by Pydantic):
    "loan":     { "amount": null, "term_months": null, ... },
    "property": { "address": null, "property_type": null, ... }
  -> Pydantic error:
       property.address       Input should be a valid string [input_value=None]
       property.property_type Input should be a valid string [input_value=None]
       loan.amount            Input should be a valid number [input_value=None]
  -> The schema permits property to be ABSENT (property: null), but if a property
     object is present its address and property_type are required non-nullable
     strings. "I have a property, and I know nothing about it" is not a state the
     schema allows, and that is deliberate: it collapses to "I have no property."

==============================================================================
 WHY THIS MATTERS FOR THE TWO-GUARANTEES QUESTION
==============================================================================
There are three distinct failure classes visible here, and each layer catches a
different one:

  malformed shape        -> caught by the tool schema / Pydantic   (attempt 3)
  arithmetic incoherence -> caught by the consistency validator     (all attempts:
                            calculated 9642.17 vs stated 10892.17, delta -1250.00)
  plausible fabrication  -> caught by NEITHER                       (attempt 1)

The third class is why the ROUTING and REVIEW patterns from System 1 exist. No
amount of schema strictness detects a well-formed lie; only an independent signal
compared against the source document does.
